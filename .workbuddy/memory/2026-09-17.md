# 2026-09-17

## musicm — 网络音乐文件系统规划（飞牛 NAS）

Delivered a full design plan for `musicm` (Rust): expose 网易云音乐 / QQ音乐 libraries as a
local filesystem so 飞牛音乐 (fnOS native music app) can scan and play them.

### Decisions taken
- Repo is a Rust project (`Cargo.toml`, named `musicm`), currently an empty `main.rs` — the plan
  targets Rust, not Python/Go.
- **Do NOT reimplement 网易云 weapi/eapi crypto in Rust.** Run the Node API services as Docker
  sidecars (`api-enhanced` for 网易云, `jsososo/QQMusicApi` for QQ) and treat them as plain HTTP.
  This keeps cookie/风控/解灰 logic out of the Rust codebase.
- Two interchangeable frontends over one virtual-FS core:
  - **Plan A — FUSE** (`fuser` crate), mounted on the fnOS host at `/vol1/1000/<EnglishPath>`.
    Must be host-level (a container mount is invisible to host apps). systemd unit with
    `After=network-online.target`, `/etc/fuse.conf` needs `user_allow_other`, mount options
    `allow_other,default_permissions,nonempty,umask=022,auto_unmount`.
  - **Plan B — WebDAV** (`dav-server`), consumed by fnOS native 远程挂载. Zero root, upgrade-safe.
    Try this first.
- **扫描/播放必须分离**: `readdir`/`getattr` are served only from a SQLite index (zero network)
  so the 飞牛音乐 scan of a multi-thousand-track tree does not time out. Only `read()` triggers a
  download.
- **Tag injection is mandatory, not optional**: 飞牛音乐 FAQ states missing metadata breaks
  cover/lyric scraping. On first read, download → inject ID3/FLAC Vorbis tags + cover via `lofty`
  → write `.lrc` sidecar → atomically land in the disk cache → serve bytes.
- Quality fallback chain per track: 母带 → hires → lossless → exhigh → standard, chosen from the
  API privilege data; tracks that are unplayable are excluded at index time (not at open() time,
  to avoid EIO during scan).
- Root path must be pure English (fnOS FAQ); virtual tree names must be sanitized for
  `/ \ : * ? " < > |` and length.

### Verified environment facts
- 飞牛音乐 launched Aug 2026; scans folders granted in 应用中心, supports 网盘/远程设备 sources,
  does **not** have an online catalog.
- fnOS host-level `rclone mount` into `/vol1/1000/...` is a known-working pattern on fnOS and is
  visible to other fnOS apps (confirmed via fnOS forum). fnOS ships a stripped-down rclone —
  install the full `.deb` if rclone is used.
- `https://vol1` style paths: fnOS storage is `/vol1`, `/vol2`; user dirs are `/vol1/1000/...`.

## musicm — 歌单扫描 + 单曲落地（已实现并实测通过）

Runtime target was pinned by the user to **fnOS (Debian) / aarch64**, which changed dependency
selection. Built and verified the first milestone end-to-end on Windows x86_64.

### Modules (src/)
`main.rs` (clap CLI) · `config.rs` (quality ladder, ApiMode, cookie) · `model.rs` (unified Track/
Playlist/AudioInfo/CachedFile, `now_secs`) · `naming.rs` (cross-platform safe path segments) ·
`store.rs` (JSON index, atomic save) · `netease.rs` (HTTP client + lenient deserializers) ·
`tag.rs` (lofty tag writing, LRC timestamp stripping) · `fetch.rs` (resolve → download → tag →
atomic rename).

### Deviations from the original plan (deliberate)
- **JSON index instead of SQLite.** `rusqlite` bundled needs a C toolchain on the NAS. JSON is
  fine for the target scale (thousands of tracks); revisit with `redb` at ~100k.
- **`ureq` 3.4 (rustls) instead of reqwest.** No OpenSSL, no tokio, ~4 MB release binary.
  `ring` is the only C-compiled dep — `apt install build-essential` on the NAS covers it.
- **Only the direct (anonymous) 网易云 transport is implemented.** `ApiMode::Sidecar` exists in
  config with correct paths but is untested; it's needed for cookie/解灰Vip tracks.

### Verified behaviour (real API, anonymous)
- `scan 3778678` (热歌榜): 200 tracks in **1** HTTP request; 131 of them (66%) are VIP-only.
- Free-tier (`fee = 8`) tracks resolve to 320k mp3 anonymously; `fee = 1` returns `code = -110`.
- Requesting `lossless` (`br=999000`) may return a 320k mp3 — the server's actual level is
  recorded separately (`AudioInfo::actual_level`) so logs don't lie.
- Download → ID3v2.3 written (version byte verified = 3), cover embedded (JPEG SOI at offset
  1516), `.lrc` + `cover.jpg` written, second run hits the cache. `cargo test`: 9 passed.

### API traps found the hard way (now handled by `flex::*` deserializers in netease.rs)
`no`/`disc` arrive as `"01"` strings; `type` is `null` for unavailable tracks (the worst one —
it turned a readable "needs login" into a parse error); `data`/`songs` can be `null` instead of
`[]`; playlist `tracks` can contain `null` placeholders. Reusable write-up lives in the
user-level skill `netease-music-api`.

## musicm — FUSE 出口（已实现，Linux 专属代码已交叉编译验证）

Implemented the read-only FUSE export. Split so that the risky part is testable off-Linux:

- `vfs.rs` (new, platform-independent): the virtual tree. Stable inode allocation via a
  persistent `rel -> ino` map (never renumber), `lookup`/`children`/`abs`/`adopt`, hidden-file
  skipping (`.xxx.part.mp3`), and `Materializer` trait so the tree core never learns about 网易云.
- `fuse_fs.rs` (new, `#[cfg(target_os = "linux")]`): thin adapter over `fuser 0.18`.
- `materialize.rs` (new): `LibraryMaterializer` bridges the tree to the real source;
  `OfflineMaterializer` is the `cached`-mode stand-in.
- `fetch.rs` refactored: `ensure_stem(track, dir, stem, force)` is now the primary entry —
  the caller (index or virtual tree) owns the path, so FUSE and CLI can never disagree.
  `Fetcher::fetch()` is a convenience wrapper that computes dir+stem from the index.
- `naming.rs`: added `group_rel()` and `unique_stems()`; deleted `track_rel_path` /
  `lrc_rel_path` / `cover_rel_path` (dead after the refactor). `group_rel` returns `String`
  with `/` separators, not `PathBuf` — a test caught that `PathBuf` yields `\` on Windows,
  which would have been a silent separator drift between the tree and the disk.

### Verified
- `fuser 0.18` has `default = []`; without the `libfuse` feature Linux uses the pure-rust mount
  path (`build.rs` sets `cfg(fuser_mount_impl="pure-rust")`) via `fusermount3`.
  **No `libfuse-dev` needed** — only `apt install fuse3` at runtime. Confirmed by cross-checking.
- Real-data tree build (index from the earlier `scan 3778678` + the one downloaded track):
  3 dirs / 202 files (200 tracks + cover.jpg + 1 .lrc), 12.0 MB on disk, 199 pending.
- `cargo test`: 21 passed. `cargo build`: zero warnings. Release binary 3.91 MB.

### The verification gap (important)
`fuse_fs.rs` is invisible to a Windows build. Proven empirically: injecting a deliberate type
error into it left `cargo build` at **exit 0 in 0.12s** (it didn't even trigger a rebuild),
while the cross-check failed immediately. Added `tools/linuxcheck/` — a separate crate that
`#[path]`-includes the real source files and is checked with
`cargo check --target aarch64-unknown-linux-gnu` (that target was already installed).
Technique written up as the user-level skill `rust-cross-target-check`.

### Next
`--fuse-mode ondemand` makes a full 飞牛音乐 library scan equivalent to downloading the whole
playlist (the scanner reads metadata from every file), so **`cached` is the mode to point the
scanner at**. That makes M3 (prefetch queue / cache quota) the natural next step, not WebDAV.

## musicm — 交叉检查的盲区（NAS 上编译暴露的 E0277）

The first real Linux build (on the NAS) failed with exactly one error:

```
error[E0277]: `PathBuf` doesn't implement `std::fmt::Display`
--> src/main.rs:541:27  |  println!("已卸载 {mountpoint}");
```

Windows `cargo build` was green with zero warnings and 21 passing tests. The cause was not the
typo but **where the code lived**: `mount_now` was two `#[cfg]`-gated fns inside `main.rs`.
Windows compiled only the non-Linux one; `tools/linuxcheck` never referenced `main.rs`. So the
Linux branch was compiled by nobody — a blind spot in the very guard added to prevent blind spots.

### Fix (structural, not just the typo)
Extracted both branches into a new `src/mount.rs` (with `MountArgs`), `#[cfg]` **inside** the
file, and `mod mount;` unconditionally in `main.rs`. Now Windows `cargo build` compiles the
non-Linux branch and the cross-check compiles the Linux branch — every line is compiled somewhere.
`main.rs` keeps only `#[cfg(target_os = "linux")] mod fuse_fs;` (a module *declaration*, and
that file is already in the check list). Added `#[path] pub mod mount;` to linuxcheck.

Rule going forward: **platform-specific code belongs in an always-compiled leaf module, never in
a `#[cfg]` hole cut into `main.rs`.**

### Proof the checker now covers it
Injected `let _probe: String = format!("{mountpoint}");` into `mount.rs` (wrapped in
`// __PROBE_START__ / __PROBE_END__`). Result: Windows `cargo build` **exit 0** (invisible),
cross-check **E0277 at `src\..\..\..\src\mount.rs:67`** — i.e. it resolves through `#[path]` to
the real file. Probe removed, `Grep PROBE` clean.

Note: a `cargo check` that finishes in 0.08s proves nothing (cache hit). Only the injected-probe
test proves coverage.

### Verified after the fix
`cargo build` zero warnings · `cargo test` 21 passed · aarch64 cross-check exit 0 · release 3.9 MB ·
`mount` preview still prints the tree on Windows. Skill `rust-cross-target-check` gained a section
on this failure mode.

## Cookie / QR login (M5a) — implemented and verified end-to-end

Request was "请继续实现cookie" — implement the credential path deferred earlier, to unlock the
~66% VIP-only tracks found during scanning.

### Key finding: QR login needs no crypto
The direct endpoint `https://music.163.com/api/login/qrcode/{unikey,client/login}` works over the
**plain `/api/` path with `crypto=''`** — no weapi/eapi AES+RSA. Probed with curl first:
`POST /api/login/qrcode/unikey?type=1` returned a valid `unikey`, and an unpolled `client/login`
returned `code:801`. Confirmed the whole flow is reachable without implementing any encryption.
Endpoint mapping differs by mode (Direct `/login/qrcode/*` + `/nuser/account/get` vs Sidecar
`/login/qr/*` + `/login/status`) — table added to skill `netease-music-api` §9.

### New modules
- `src/auth.rs` — `Credentials` (parse/normalize/masked), `Origin` enum, `save/load/clear/path`.
  cookie lives in `<data_dir>/cookie.txt` at **600 on Unix**; `write_private` creates it with
  `OpenOptions::mode(0o600)` (no 644→600 window), `harden()` re-tightens if it already existed.
- `src/qr.rs` — terminal QR rendering with half-block `▀` + ANSI colours (density doubling),
  pure Rust via `qrcode 0.14` with `default-features = false`.

### Files touched
`main.rs` (mod auth/qr; `Login`/`Logout`/`Whoami` subcommands; `cmd_login`, `login_by_qr`,
`read_cookie_input`, `cmd_logout`, `cmd_whoami`), `config.rs` (`resolve_cookie` with migration
priority env > cookie.txt > legacy config.json; `cookie_origin`), `netease.rs` (`post_form`
returning `(body, Set-Cookie)`, `account`, `qr_key`, `qr_poll`, `QrState`, `song_url` now branches
on `ApiMode`), `model.rs` (`now_millis`), `fetch.rs` (better login hints), plus
`tools/linuxcheck` (`#[path] pub mod auth; pub mod qr;` + `qrcode` dep).

### Three real bugs hit and fixed
1. **`skip_serializing_if = "Option::is_none"` does NOT prevent writing.** It only skips `None` —
   `Some` values are still serialized, so the plaintext cookie stayed in `config.json`.
   Fixed with `#[serde(default, skip_serializing)]`. Verified `MUSIC_U` no longer appears there.
2. **Double-save.** A global `--cookie` flag AND `login --cookie` both wrote cookie.txt
   (output printed "凭据已保存到…" twice). Removed the global flag entirely; `login` is its sole
   owner, and `Origin::Cli` was deleted from the enum.
3. **Test expected a space that `normalize` intentionally strips.** `save_load_clear_round_trip`
   wanted `"MUSIC_U=…; os=pc"`, got `"MUSIC_U=…;os=pc"`. The stripping is correct (RFC 6265:
   cookie names/values are tokens, no spaces) — the *test* was wrong. Documented in `normalize()`.

### Two API behaviours worth remembering
- `/nuser/account/get` returns `code:200 + profile:null` for **both** anonymous and expired
  cookies — no error code distinguishes them. So we can only answer "are we logged in", not "why
  not". We track whether a cookie was ever stored to word the message correctly.
- `-110` means "needs login" but has two meanings; the message now distinguishes "never logged in"
  (→ `login --qr`) from "cookie expired" (→ re-login, check `whoami` first).

### Verification
- `cargo build` exit 0, zero warnings · `cargo test` **29 passed** (8 new: auth×5, qr×3)
- aarch64 cross-check exit 0 — **and proved to cover `auth.rs`'s `#[cfg(unix)]` branch** by
  injecting `let _probe: String = format!("{path}");` into `write_private`: Windows build **exit 0**
  (invisible), cross-check **E0277 at `src\..\..\..\src\auth.rs:212`**. Probe removed, `Grep` clean.
- Sidecar mode tested live against `NeteaseCloudMusicApi` on :3210. Access log confirms the exact
  endpoints: `/login/status`, `/login/qr/key`, `/login/qr/check` ×4 (2.2 s interval),
  `/song/url/v1?id=…&level=exhigh` → real `m701.music.126.net` URL returned.
- Direct-mode QR rendering cross-checked by decoding the matrix with an independent `jsQR` decoder;
  it matched the intended URL (matrix differs from node `qrcode` only in mask selection).
- `whoami` against a fake token correctly reported 未登录; `info` shows masked credential + origin;
  legacy `config.json` migration verified to remove the plaintext.

### Environment gotchas re-confirmed
- `cargo check --target aarch64-…` **must be run inside `tools/linuxcheck`**. At the repo root it
  fails on `ring`'s build script looking for `aarch64-linux-gnu-gcc` — that's a wrong-directory
  symptom, not a code error. Noted in both the skill and MEMORY.md.
- PowerShell reaps child processes when the call ends; a background sidecar must be started with
  `run_in_background: true` or it is killed before the next call can reach it (cost one wasted run).

## `code=8821` — QR login is blocked by 风控; made it a terminal state

User reported, after scanning the QR: `接口返回了预期外的状态（code=8821…），继续等待`,
and noted their NetEase app was already the latest version.

### What 8821 actually is
Searched it out: **`8821` = 需要行为验证码验证** (the response also carries
`redirectUrl: https://qa-yyy.igame.163.com/anquanhuanjingfengxian` = 安全环境风险).
NetEase's risk control decided the login request doesn't look like an official client and wants a
slider/click captcha — which a CLI/third-party client can never provide. Community projects have
given up on QR because of this; `ncmctl`'s docs state plainly that QR login is unsupported due to
8821.

Crucially, **it fires *after* the scan succeeds**, not before — the app shows "confirmed", then the
poll returns 8821. That's why it reads like a slow network and why re-scanning is useless.

Ruled out the parameters empirically (curl probes, all → `801`):
- `unikey` with `type=1` and `type=3` both return a valid key; `type=0`/absent → `400`.
- Polling with `type=1`/`type=3`, including cross-combinations, is **completely equivalent**.
So it's risk control, not a parameter bug.

### The real bug on my side
`QrState::Unknown` lumped together two opposite things:
- an empty `{}` from the sidecar (transient — keep polling), and
- a terminal rejection like 8821 (stop now).

Result: the terminal case silently degraded into "keep waiting" and burned the whole 5-minute
timeout before failing. Split into `Empty` (code 0), `Blocked` (8821), `Unrecognized` (anything
else, still polls but prints the raw code + message), with `QrState::is_terminal()` as the single
decider. The loop now carries a `debug_assert!` invariant so that adding a future terminal state
without handling it can't silently regress to waiting.

`8821` now prints a full "switch to cookies" walkthrough instead of "继续等待".

### Verified with a mock sidecar (no real scan needed)
Wrote tiny Python HTTP servers mimicking the sidecar, pointed `MUSICM_API_BASE` at them:

| mock returns | elapsed | `/login/qr/check` calls | expected |
|---|---|---|---|
| `8821` | **2.6 s** | **1** | stop immediately ✔ (vs 60 s timeout / ~30 polls) |
| `4711` (unknown) | 8.2 s | 4 | keep polling to timeout ✔ |

The second case matters as much as the first: it proves the fix didn't over-correct by treating
every unfamiliar code as fatal.

### Environment finding
`ureq` honours `HTTP_PROXY`/`HTTPS_PROXY`. This sandbox sets them to `http://127.0.0.1:52586`,
so a request to a loopback mock failed with `CONNECT proxy failed: proxy server responded 502`.
Two consequences: (a) local test servers need `NO_PROXY` or a cleared proxy; (b) **running through
a proxy means a datacenter egress IP, which by itself raises the odds of 8821** — worth ruling out
when diagnosing. (The 502 specifically was the mock having been reaped by `Start-Process`, not the
proxy's fault; a background task fixed it.)

### Verified after the change
`cargo build` exit 0, zero warnings · `cargo test` **34 passed** (5 new `netease::tests::*`:
code mapping, risk-control-vs-empty separation, terminality, unknown-codes-still-poll) ·
aarch64 cross-check exit 0.

Skill `netease-music-api` gained a full `8821` section (including "don't build your main path on
QR") and a "cookie paste is the primary path" section.

### Recommendation carried forward
Treat cookie paste as the main login path; keep QR as a best-effort option. Revisit M5b (VIP track
fetch success) only once the user is actually logged in via cookie.

## `musicm daily` — implemented (supersedes "未落码" above)

User picked the **standalone command** over the pseudo-playlist (option: "独立 daily 命令") —
the daily list changes every day, and a pseudo-playlist would pile one-off tracks into the index.

### What was added
- `netease.rs`: `DailyOutcome { tracks, code, shape }`, `DailyShape {Recommend, DailySongs,
  Missing}`, `NetEaseClient::daily_songs()`, `DailyEnvelope::pick()`.
  Path differs by mode: Direct `/v1/discovery/recommend/songs`, Sidecar `/recommend/songs`
  (+`timestamp=` to defeat its 2-minute URL cache).
- `RawTrack` gained `#[serde(alias = "ar" / "al" / "dt")]` — the App-style shape used by
  `data.dailySongs` names artists/album/duration differently.
- `main.rs`: `Daily { limit: 30, fetch: 0 }` subcommand, `cmd_daily`, `explain_empty_daily`,
  `fetch_daily`, `landed_stems`, `display_path`, `DAILY_GROUP = "每日推荐"`.

### The design point worth keeping
`#[serde(default)] Vec<..>` makes "field is an empty array" and "field is absent" collapse into
the same value — and those are the *only* two facts that distinguish "not logged in" from
"the API changed shape". So `flex::MaybeList` has three states (Missing / Empty / Items), the
same three-way split that fixed the 8821 bug. Five tests lock it down, incl. the pair
`daily_silent_empty_is_not_an_error` / `daily_empty_field_differs_from_missing_field`.

### Verified
- Live anonymous run: `daily` prints `接口 code=200，读到的是 recommend` + the cookie walkthrough
  instead of a bare "0 首" — i.e. the silent-empty trap is handled.
- End-to-end against a mock sidecar (temp `--data-dir`/`--out`, fake `dailySongs` + audio + lyric
  + cover): 3 tracks listed, the duplicate name became ` (2)`, files landed in
  `网易云/每日推荐/` with `.lrc` + `cover.jpg`; tag writing failed on the fake bytes → warning
  only, file still landed. Second run: all three "已落地" and 跳过（已在库中）×3 — the disk
  re-lookup works. (Mock's first start failed: `TCPServer` lives in `socketserver`, not
  `http.server`.)
- Fixed a cosmetic bug found in that run: the printed path was `...\library\网易云/每日推荐`
  (mixed separators). Added `display_path()` mirroring `vfs::abs`.

### Unrelated failing test found in the working tree (fixed)
`src/auth.rs` had uncommitted work adding `dedupe` + `extract_cookie_header`; its own test
`pasted_cookie_header_value_is_accepted` was red, because the label `cookie:` was only
recognized when the input contained quotes (the cURL path). The two tests were reconcilable:
recognize `cookie:` **only at the start of the input**, so `MUSIC_U=abc; note=cookie:x`
(no quotes, `cookie:` inside a *value*) is left alone. Added
`cookie_label_is_read_case_insensitively` for the `Cookie:` spelling.

### Gate
`cargo build` exit 0, zero warnings · `cargo test` **45 passed / 0 failed** ·
aarch64 cross-check exit 0 (3.27 s, real re-check — it covers the `auth.rs` edit).
`--fetch` has only been exercised against the mock: no real daily list has been fetched yet
(the machine has no cookie.txt), so the *authenticated* response shape is still unverified.

## `musicm search` + `musicm artist` + `playlists --remote` — implemented

User asked for two things: "添加搜索功能可以搜索歌单/歌曲/歌手" and "能够列出自己的歌单".

### Probed the endpoints before writing any parser
Wrote a throwaway Python prober (temp dir, explicit `ProxyHandler({})` to dodge the sandbox proxy —
an outbound proxy means a datacenter IP, which is what raises 风控 odds). Findings, all
**anonymous, direct `/api/` prefix**:

| endpoint | note |
|---|---|
| `/api/search/get/web?s=&type=1/1000/100&offset=&limit=` | 1=单曲 1000=歌单 100=歌手；`code:200` |
| `/api/user/playlist?uid=&limit=&offset=` | **`playlist` is at the TOP LEVEL**, not under `result` |
| `/api/artist/top/song?id=` | `songs` at top level, App-style names (`ar`/`al`/`dt`); **`limit` is ignored** (asked 5, got 50) |

Three traps that drove the design:

1. **Empty search results delete the array field.** `{"result":{"playlistCount":0},"code":200}` —
   no `playlists` key at all. Treating "array absent" as "API changed shape" would tell the user
   the code is broken every time they search a rare word. So `ListShape` has three states and the
   discriminator is *both* signals missing (`classify(list_present, len, count)`), with the count
   field read via a new `flex::as_opt_u64` — `#[serde(default)]` would have flattened "0" and
   "absent" into the same value and thrown the evidence away. Verified live: searching
   `zzqqxxvbnm --type playlist` prints 没有匹配的结果, not 接口结构变了.
2. **Search results carry no album cover.** The song's `album` object has `picId` but no `picUrl`,
   so downloading straight from search output loses the cover — and 飞牛's scraper keys on it.
   `--fetch` therefore calls `songs_detail(&ids)` first. Confirmed on the real download: the
   landing dir has `cover.jpg` (120 KB).
3. **`subscribed` is `null` when anonymous** (unknown, not false) → `flex::as_opt_bool` +
   `Option<bool>`; the UI marks 收藏 only on `Some(true)` rather than inventing "not collected".

### What was added

## Assessment — Docker containerisation (analysis only, no code yet)

User asked whether the app can run in a Docker container. Read-only investigation, no changes.
Repo has **no Dockerfile / docker-compose** and has never been run in a container.

Findings that matter, verified against the source and against `fuser 0.18`'s vendored code
(`~/.cargo/registry/.../fuser-0.18.0/src/mnt/fuse_pure.rs`):

- Everything except `mount` is container-clean: pure Rust + rustls (no OpenSSL), single binary,
  no `/etc`/`/proc`/`/dev` reads, atomic index writes (tmp + rename), `MUSICM_HOME`/`--data-dir`/
  `--out`/`MUSICM_OUT`/`MUSICM_COOKIE`/`MUSICM_API_BASE` all env-overridable, and `login` is
  non-interactive (`--cookie`, `--cookie-file`, stdin pipe gated on `is_terminal()`).
- `mount` needs `/dev/fuse` + `SYS_ADMIN` **and** `fuse3` (pure-rust mount path shells out to
  `fusermount3`; `FUSERMOUNT_PATH` can override it). `--allow-other` additionally needs
  `user_allow_other` in `/etc/fuse.conf` — absent in a stock image, so it must be written in the
  Dockerfile.
- **The real blocker is mount propagation, not privileges.** The mount lands in the container's
  mount namespace; the host 飞牛音乐 process cannot see it unless the volume is bound `:rshared`
  (or the container shares the host mount ns). `MusicFs::attr` reports the mounting process's
  uid/gid, so a `--user` container changes what the host sees.
- Recommended container shape: container does download/sync only, `--out` points at a shared
  volume, 飞牛音乐 scans the volume directly — zero privileges, no FUSE. FUSE stays a host
  (systemd) concern; WebDAV (M4b, still unimplemented) is the container-native FUSE replacement.

## `musicm serve` — Web admin UI (M7) — implemented and smoke-tested

User asked: "为当前应用实现一个前端管理页面，可以搜索，登录，挂载等操作".

### What was built
- `src/web.rs` (new): an **HTTP/1.1 server hand-written on `std::net`, zero new
  dependencies**. `axum` would pull tokio/hyper/tower (expensive first build on aarch64);
  `tiny_http` is light but 200 lines of `std` buys the same thing when the only client is our
  own page. Deliberate limits, each documented at the code: `Connection: close` only,
  `Content-Length` bodies only (no chunked), no HTTPS.
- `src/web/{index.html,app.css,app.js}` (new): vanilla JS, no CDN, no framework, embedded via
  `include_str!` so the NAS binary is self-contained. Views: 概览 / 搜索 / 音乐库 / 每日推荐 /
  账号 / 挂载, plus a job drawer.
- `main.rs`: `serve [--listen 127.0.0.1:8765] [--token T] [--no-auth]` + `cmd_serve`.

### Design decisions worth keeping
- **Auth: non-loopback listen requires a token**, auto-generated and printed as a
  ready-to-click URL if omitted; `--no-auth` opts out with a warning. The UI can rewrite
  credentials and write into the music library, so an open LAN port isn't acceptable. Token
  is enforced on `/api/*` only — static assets have to load so the user can type a token.
- **`src/web.rs` must NOT go into `tools/linuxcheck`.** It depends on `netease`/`fetch`
  (→ `ureq`/`ring`), and linuxcheck deliberately keeps only pure-Rust deps. It's
  platform-independent so host `cargo build` covers it — which is exactly why every
  platform-specific bit lives in `mount.rs`.
- Long ops (scan / download) run as **background jobs** with a polled append-only log. Each job
  reloads `Config`/`Index` itself instead of sharing mutable state (`Index` isn't `Clone`, and a
  long-held lock would stall every other request). `Shared` also re-`Config::load`s per request,
  so hand-edited `config.json` shows up on refresh.
- `/api/play` writes back to the index (same route as `musicm play`); `/api/fetch` deliberately
  doesn't (matches `daily --fetch`, so daily shoves don't pollute the index).

Duplicating these would have let CLI and Web disagree, so they moved to shared homes:

- New `Index::remember_track` — landing a track found via search now records its metadata too,

invisible until the mount is redone. Inode stability is the stated reason the tree isn't rebuilt

## mount — 日推落地后自动出现 + 放开空索引挂载（已实现）

User picked "两个都修" from the two gaps above.

### `Vfs::refresh` — 增量重扫（`vfs.rs`）

- Extracted the body of `Vfs::build` into a private `Vfs::load` (index-expected ∪ on-disk), so
  `build` and `refresh` are literally the same code path and cannot drift on inode semantics.
- `refresh` measures before/after and returns `RefreshStats { added, materialized }`.
- **Two decisions worth keeping:**
  - **Merge, never rebuild.** Rebuilding renumbers every inode; the kernel's dentry cache keys on
    them, so a file being played would suddenly read different bytes.
  - **Additive only, never delete.** Removing nodes whose path is missing races with `adopt`: the
    fetch flow is "placeholder with a guessed extension → land → adopt renames", and in that window
    the guessed path genuinely doesn't exist. A rescan that treated "missing on disk" as deletion
    would delete nodes that are mid-fetch. Cost accepted: manually deleted files linger until
    remount.
- **Bug caught by my own test:** `materialized` was first counted as "materialised node count went
  up", which also counts freshly landed files (they're born materialised). The test asserted
  `materialized == 0` for a pure new-file scan and failed 1 vs 0. Now it counts only inodes that
  were *pending before* the refresh and are landed after — see `Counts::pending` (a `BTreeSet<u64>`
  of pending inodes; `Counts` had to drop `Copy`).
- Two tests: `refresh_picks_up_new_files_without_renumbering` (new 每日推荐 file appears, old
  file's inode unchanged, daily file carries no track key) and `refresh_upgrades_pending_in_place`
  (pending → materialised with the same inode, no extra readdir entry).

### `RefreshGate` — 间隔闸门放在 `mount.rs`（`mount.rs` + `fuse_fs.rs`）

The gate logic ("once per interval, record the *attempt* not the success") would have lived in
`fuse_fs.rs`, which **never compiles on Windows** — i.e. permanently untested. Moved to `mount.rs`
(the always-compiled leaf module, same reasoning as the file header) with two tests
(`stays_closed_within_the_interval`, `consumes_its_turn` + a `#[cfg(test)] rewind` helper).
`fuse_fs` now holds a `RefreshGate` and calls `maybe_refresh()` at the top of `readdir`:
`Index::load` (fresh read → newly scanned playlists land too) → `vfs.lock()` → `vfs.refresh(...)`.
Failures only skip that round; a read-only FS must not turn `readdir` into EIO because the index
was momentarily mid-write. `mount::REFRESH_SECS = 30` is shared with the CLI hint so the number
can't drift into a lying message.

### `cmd_mount` — 判据换成「树里有没有东西」

Was `index.stats().tracks == 0 → bail`, which rejected exactly the daily-only library the user is
building. Now: build the tree first, error only when `tree.files == 0 && indexed == 0`; print
targeted hints for "index empty but disk has files" and "index non-empty but cached tree empty".
Four boundary cases smoke-tested on Windows (the non-Linux branch prints the real tree):
daily-only library mounts (`网易云/每日推荐/ 7 项`) · with index cached/ondemand · empty lib with
index (hint) · empty lib without index (error).

### Gate

`cargo build` zero warnings · `cargo test` **71 passed / 0 failed** · aarch64 cross-check zero
warnings. The cross-check's 0.2 s runtime looked like a cache hit, so coverage was **proved with a
probe** (`let _probe: String = 123u32;` in `maybe_refresh` → `error[E0308] at
src\..\..\..\src\fuse_fs.rs:180`), then removed and re-verified clean. The readdir hook itself can
only be exercised on Linux — `Vfs::refresh` and `RefreshGate` are covered by unit tests, the wiring
is compile-verified only.
